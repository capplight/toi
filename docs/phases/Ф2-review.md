## 3. Обязательные правки

### Б1 (блокирующее, безопасность). Вход по ссылке привязывает все членства с этим телефоном

Хозяин выдаёт ссылку составителя и **сам видит её URL** (`issueLoginLinkAction` возвращает `url`). Значит, ссылка доказывает не владение номером, а только то, что хозяин события A допускает этот номер в своё событие.

Как сейчас:
1. Хозяин A добавляет телефон P (например, родственника, который составляет список в чужом событии B).
2. Хозяин A выдаёт ссылку и открывает её сам.
3. `consumeLink` создаёт сессию пользователя P и привязывает **все** членства P.
4. Хозяин A видит список гостей события B.

Плюс два побочных эффекта:
- `revokeMemberSessionsAction` в событии A отзывает **все** сессии P, включая вход в событие B;
- четыре таких входа подряд вытесняют настоящие сессии P (лимит 3).

Что сделать (план v1.5, 6.1 «Область доступа сессии», схема 5):
- `sessions.scope` (`'all'` | `'events'`) и таблица `session_events (session_id, event_id)`;
- вход по ссылке составителя: привязать **только** членство из ссылки, сессия `scope = 'events'` с этим событием. Если на устройстве уже есть сессия того же пользователя со `scope = 'events'`, добавить событие в неё;
- вход по SMS и по ссылке основателя (`owner_bootstrap`): `scope = 'all'`, привязать все членства телефона (как сейчас);
- `authorize`: проходит, только если `scope = 'all'` или событие есть в `session_events` текущей сессии (`requireUser` должен вернуть `sessionId` и `scope`). Список `/e` для `scope = 'events'` — только эти события;
- `revokeMemberSessions(memberId)`: удалить событие из `session_events` сессий этого пользователя и отозвать сессии, у которых событий не осталось. Сессии `scope = 'all'` не трогать;
- лимит 3 сессий — отдельно для `scope = 'all'` и для `scope = 'events'` (на событие). Сессии по ссылкам не вытесняют SMS-сессии;
- вход по ссылке не меняет `users.locale` уже существующего пользователя.

Тесты (integration):
- «хозяин A открывает ссылку составителя P, который есть в событии B» → в B 403, в `/e` только A;
- «Шығару» в A не трогает SMS-сессию P;
- вход P по SMS после этого → доступ к A и B;
- два входа по ссылкам разных событий на одном устройстве → одна сессия с двумя событиями.

### Б2 (обязательно). Код для неизвестного номера

Для неизвестного номера сохраняется проверка (`provider = 'none'`) со случайным кодом, и `verifyOtp` её принимает, если код угадан (5 попыток из миллиона). Вероятность мала, но последствия неприятные: появляется пользователь с этим телефоном и действующая сессия `scope = 'all'`. Если номер позже добавят составителем, а настоящий владелец войдёт по SMS, старая сессия того, кто угадал код, получит доступ (тот же `users.id`).

Исправление: `verifyOtp` никогда не принимает проверку с `provider = 'none'` (ответ — как на неверный код: попытки считаются, ответ тот же). Тест.

### Б3 (обязательно, переносится из Ф11 в Ф2). Очистка служебных данных

`/api/cron/cleanup` (план 6.7) с `Authorization: Bearer CRON_SECRET`, раз в сутки через Vercel Cron (`vercel.json` → `crons`). Удаляет:
- `otp_challenges` старше 24 часов — там телефон и IP, в том числе неизвестных номеров (отклонение 4);
- `rate_limits` старше 2 суток;
- `login_links` использованные, отозванные или истёкшие больше 30 дней назад;
- `sessions` отозванные или истёкшие больше 30 дней назад;
- строки `session_events` удаляются каскадом.

Integration-тест на каждую таблицу и на 401 без секрета.

После правок: перезапустить `typecheck`, `lint`, `test`, `test:integration`, e2e; дописать в `Ф2-handover.md` раздел «Правки по ревью».
