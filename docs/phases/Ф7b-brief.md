## 1. Цель

Составитель с правом рассадки видит зал на телефоне и компьютере, понимает проблемы (переполнение, дубли, без места) и решает их в несколько нажатий:
- переносит семью;
- меняет порядок категорий — без автопересадки;
- запускает полную пересадку только с предпросмотром;
- отменяет любое своё действие из истории.

Составитель «Тек тізім» всё это видит, но ничего не меняет.

  Доступ — `requireMember(…, {seating: true})`; чтение — `requireMember`.
- [ ] **Правила истории и отмены (ревью Ф4):**
  - запись `createCategory` (`summary.reason = "categoryAdded"`) — **без «Қайтару»**;

  - отмена ответа по телефону (Ф4 `revertAnswer`) ставит исходной записи `reverted_by` — H7 показывает её зачёркнутой;
  - ответы гостей (`actor_kind = guest`) — без «Қайтару» (`hall.history.guestNoUndo`);
  - отменить можно и саму отмену (запись `undo`, план 7.6);
  - частичная отмена → `hall.history.partialUndo` с числом семей.
- [ ] **Защита адаптера:** если шаг вернул `noop: true`, а `deltas` не пусты — исключение (места не меняются без новой версии). Unit-тест.
- [ ] «Бос орынға ауыстыру» (Р3): `suggestTable` → подтверждение → `moveFamily` с `summary.reason = "suggested"`.

## 4. Тесты и приёмка

- **unit / property:** правка `undoChange` (новые категории при восстановлении порядка); защита адаптера.
- **integration:**
  - каждое действие — доступ (`Тек тізім` → 403), 409, история, `seating_version`;
  - полная пересадка: предпросмотр = применение при той же версии;
  - отмена переноса, порядка, зала, полной пересадки, в том числе частичная;
  - `reverted_by`;
  - нет «Қайтару» у `categoryAdded` и у ответов гостей.
- **e2e (360, 320, 1440; kk и ru):**
  - перенос с «Қайтару»; «Бәрібір ауыстыру»; порядок ↑↓ без пересадки; полная пересадка с предпросмотром;
  - дубли и «Схемадан көру»; история и отмена;
  - **«Тек тізім» не видит кнопок рассадки** (ревью Ф3, откл. 9);
  - два браузера (мама и папа) переносят разные семьи одновременно без потерь, второй видит изменения после опроса;
  - критерий B1 на настоящем экране «Зал» (360 и 320, хозяин);
  - axe, 130 %.
- Приёмка по плану 12.3 Ф7b + всё перечисленное; схема 20 × 16 читается на 360 px; раскладка десктопа по 8.7 (Н1 ревью Ф1).

## 6. Параллельно с РА? — Да, с правилами

Ф7b может делать второй разработчик в отдельном worktree от `phase/F6-summary`, пока первый делает локальную часть РА. **Риск конфликтов — низкий / средний, конфликты механические.** Пересечения и правила:

| Файл / область | РА | Ф7b | Правило |
|---|---|---|---|
| `VersionPoll`, маршрут версии | Л2 (затухание, `activity`) | использует | Меняет **только РА**; Ф7b берёт компонент как есть |
| `src/ui/components.css` | Л1 (список без гидратации) | стили зала | Ф7b пишет новые стили в **`src/ui/hall.css`** |
| `tests/e2e/global-setup.ts`, `worlds.ts` | возможно | новые миры `hall`, `hallConcurrency` | Добавлять отдельными блоками в конец; при конфликте оставить оба |
| `GuestsScreen` / S1 | Л1 переписывает | не трогает | Ф7b не меняет S1 |
| `undo.ts`, адаптер, сервисы зала | — | меняет | Только Ф7b |
| `EventShell` (точка «Зал») | — | меняет | Только Ф7b |

Порядок мержа: РА → Ф7b (Ф7b перебазируется на `phase/RA-prep` перед сдачей).

Если второго разработчика нет — Ф7b сразу после локальной части РА, а пункты РА с аккаунтами идут параллельно, по мере готовности аккаунтов.
