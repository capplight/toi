## 2. Производительность (вопрос 1) — решение

Цифры Л1:

| Метрика | До | После |
|---|---|---|
| Работает весь список | 1239 мс | ~800 мс |
| Первое касание | 744 мс | 801 мс (без выигрыша) |
| Документ, gzip | 22 КБ | 29 КБ |
| Встроенный RSC | 53 КБ | 108 КБ |
| Строгий тест | — | 1063 / 958 / 940 мс (первый повтор не прошёл) |

Узкое место по профилю — разбор и раскладка документа.

Удвоение RSC — следствие того, что строка HTML списка входит и в разметку, и во встроенные данные RSC. В App Router так ведёт себя любой серверный контент, и **дешёвого способа его убрать нет**. В переданных байтах это +7 КБ gzip — для слабого интернета допустимо. **Чинить удвоение до релиза A не требую.**

Решение:
1. **Л1 принимается** как есть: интерактивность всего списка — главный выигрыш на слабых телефонах.
2. **П1 (обязательно до релиза A):** сообщения клиента по страницам.
   - Сейчас корневой layout отдаёт в `NextIntlClientProvider` 18 namespaces (~25 тыс. символов) на **каждом** экране.
   - Нужно: провайдер на уровне маршрута с namespaces только этого экрана (S1 — `guests`, `guestSheet`, `common`, `send` и т. п.), общий минимум в layout.
   - Это уменьшит и документ, и разбор на всех экранах, не только на S1. Замер до и после на S1 и «Қорытынды» — в handover.
3. **Окончательное решение — по CI и Android, без дальнейших переделок до них.** Ворота релиза A прежние:
   - медиана S1 < 1 с в CI на Linux (`--repeat-each=3`, рост ≤ 30 %);
   - на недорогом Android тёплое ≤ 1 с, холодное ≤ 2 с.

   Если после П1 CI не укладывается — следующий шаг из handover: уменьшить разметку карточки (меньше узлов, иконки одним спрайтом `<use>`). Не раньше замера в CI.

## 4. Бэкап и восстановление (вопрос 3)

| Тема | Оценка |
|---|---|
| Шифрование | ✓ `age` по публичному ключу (`BACKUP_AGE_RECIPIENT`); в CI нет секрета для расшифровки; приватный ключ у основателя вне репозитория |
| Поток | ✓ `pg_dump -Fc --no-owner --no-privileges` сразу в `age`, без открытого файла на диске раннера; `test -s`; загрузка в R2 и проверка `ls` |
| Отдельный бакет | ✓ `BACKUP_R2_BUCKET` (не бакет медиа), токен ограничен этим бакетом. Окружение GitHub `production` |
| Срок хранения | ✓ Удаление старше 30 дней по имени-метке. Рекомендация: продублировать правилом жизненного цикла R2 (Н2) |
| Версия клиента | ✓ `postgresql-client-17` из PGDG — читает Neon 16 и 17 |
| `restore.sh` | ✓ Отказы: URL с `prod` / `production`; **цель не пуста** (таблицы в `public`) — главная защита, прод всегда не пуст. Расшифровка во временную папку, `trap` удаляет её; `pg_restore --exit-on-error`; проверка числа строк по таблицам из оглавления дампа, `--compare` с источником. Проверено на Postgres 17.6 |
| Роль БД для дампа | Рекомендация (Н1): отдельная роль только на чтение для `PROD_DATABASE_URL_UNPOOLED` бэкапа, а не владелец |

Что сделать при первом запуске (раздел 2 брифа РА): основатель расшифровывает первый настоящий бэкап **своим** ключом. Приватный ключ хранится в двух местах: менеджер паролей и офлайн-копия. Без ключа бэкапы бесполезны — внести в RUNBOOK (Н3).
