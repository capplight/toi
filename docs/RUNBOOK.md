# «Той» — RUNBOOK (пилот, релиз A)

Версия 1.0 · 2026-10-12 · разработчик (агент), РА Л4. Для основателя и того, кто дежурит в день тоя.
Окружения:
- прод — `toi-pilot.vercel.app` (Vercel, регион `fra1`) + Neon (Франкфурт) + Cloudflare R2;
- preview — ветки Neon и деплои Vercel на каждую ветку.

План: 9 (безопасность, бэкапы), 11.2–11.3 (окружения, CI/CD), 14 (чек-лист пилота).

> Ничего из этого не делать «на глаз» в проде. Сначала прочитать раздел целиком, потом действовать по шагам. Всё, что вводится в консоль, — с переменными прода из Vercel (`vercel env pull .env.production.local`, файл не коммитится; удалить после работы).

---

## 1. Выпуск

1. Ветки сливаются в `main` **по порядку цепочки**: F0 → F7a → F2 → F1 → F4 → F3 → F5 → F6 → RA → …
   - Каждая — после зелёного CI: unit, integration, e2e на Postgres 16, `guests-perf` ×3, Docker, gitleaks.
   - Защита `main` требует CI.
2. Пуш в `main` запускает `.github/workflows/deploy-prod.yml`, если в репозитории есть переменная `PROD_DEPLOY_ENABLED = true` (GitHub → Settings → Secrets and variables → Actions → Variables). Пока её нет, пуш деплой пропускает, ручной запуск (Run workflow) работает всегда:
   1. `pnpm check:messages` (тексты, готовые тексты приглашений, свежесть `legal.generated.ts`) и **`pnpm check:legal:strict`**: пока в `content/legal` есть пометки `[ЮРИСТ …]`, деплой прода **падает** (ревью РА, П3). Локально и в preview — только предупреждение;
   2. **миграции** прода (`pnpm db:migrate` с `PROD_DATABASE_URL_UNPOOLED`). Миграции только расширяющие: старый код работает с новой схемой;
   3. сборка `vercel build --prod` и деплой готовой сборки.

   Vercel сам `main` не деплоит (`vercel.json`). Коммиты только в `docs/`, `design/` и т. п. прод не перевыкладывают.
3. После деплоя:
   - `https://toi-pilot.vercel.app/api/health` → `ok`;
   - открыть свой тестовый той;
   - открыть одну ссылку гостя `/i/…`.
4. Ручной перезапуск — GitHub → Actions → «Deploy production» → **Run workflow**.

## 2. Откат

- **Код:** Vercel → Project → Deployments → предыдущий рабочий деплой → **Promote to Production** (мгновенно, без сборки). Потом исправить в `main` и выпустить заново.
- **База:** миграции **не откатываются**. Они расширяющие, поэтому предыдущий код работает с новой схемой — откатить только код.
  - Если миграция испортила данные — раздел 3 (восстановление в ветку Neon), затем перенос нужных строк.
  - Вариант: Neon → **Restore** ветки на момент до миграции (point-in-time в пределах хранения истории тарифа).
- Не делать `git revert` миграций и не править `db/migrations` задним числом.

## 3. Восстановление из бэкапа

Бэкап: `.github/workflows/backup.yml`, ежедневно в 02:30 по Алматы, когда в репозитории есть переменная `BACKUP_ENABLED = true` (включить после секретов R2 и ключа age).
- `pg_dump -Fc` → шифрование `age` → отдельный бакет R2 `daily/toi-<время>.dump.age`;
- хранение 30 дней;
- закрытый ключ `age` — только у основателя, вне репозитория и вне GitHub.

**Ключ `age` (ревью РА, Н3) — без него бэкапы бесполезны:**
- Пару создаёт основатель на своей машине: `age-keygen -o toi-backup.txt`. Строка `# public key: age1…` — в секрет `BACKUP_AGE_RECIPIENT`.
- Закрытый ключ (`AGE-SECRET-KEY-…`) хранится **в двух местах**:
  1. менеджер паролей;
  2. офлайн-копия (распечатка или флешка в надёжном месте).

  В репозиторий, GitHub, Vercel и мессенджеры он не попадает.
- **Первый настоящий бэкап основатель расшифровывает сам**, своим ключом, и восстанавливает по шагам ниже в новую ветку Neon. Так проверяется, что ключ действительно подходит. Результат — в протокол РА.

**Настроить вместе с аккаунтами (ревью РА, Н1–Н2):**
- **Н1.** Для бэкапа — отдельная роль Neon **только на чтение**, не владелец базы:
  ```sql
  create role toi_backup login password '…';
  grant pg_read_all_data to toi_backup;
  ```
  Её прямой URL — в `PROD_DATABASE_URL_UNPOOLED` окружения бэкапа. Если GitHub-окружение `production` общее с `deploy-prod.yml`, которому нужен владелец для миграций, бэкапу дать отдельный секрет и поменять имя в `backup.yml`.
- **Н2.** На бакете бэкапов R2 — правило жизненного цикла «удалять объекты с префиксом `daily/` старше 30 дней». Оно дублирует шаг удаления в `backup.yml`.

**Пробное восстановление (план 14) и настоящее:**
1. Скачать нужный файл из R2 (Cloudflare → R2 → бакет бэкапов → `daily/`), например `toi-2026-12-01T213012Z.dump.age`.
2. Создать **пустую** ветку Neon (Neon → Branches → New branch; или пустую базу в той же ветке) и взять её прямой URL (не `-pooler`).
3. На машине с `pg_restore`, `psql` (версия ≥ версии дампа) и `age`:
   ```
   scripts/restore.sh toi-2026-12-01T213012Z.dump.age "postgres://…/neondb?sslmode=require" --identity ~/keys/toi-backup.txt
   ```
   - Скрипт расшифрует файл, восстановит базу (`--no-owner --no-privileges`, остановка на первой ошибке) и проверит, что каждая таблица из дампа есть, с числом строк.
   - `--compare <URL прода>` сравнит числа с продом — имеет смысл сразу после свежего бэкапа.
   - На URL с `prod` / `production` скрипт не работает, а в непустую базу не восстанавливает.
4. **Если прод потерян:** восстановить в новую ветку → проверить → сделать её основной в Neon (или поменять `DATABASE_URL` / `DATABASE_URL_UNPOOLED` в Vercel на новую ветку) → **Redeploy** в Vercel. Потом раздел 5 (сессии остаются действительны — они в той же базе).
5. Файлы (музыка, обложки) лежат в R2 отдельно, бэкап базы их не содержит. В R2 они не удаляются при откате базы.

## 4. Ссылка хозяину пилота

Хозяин входит по одноразовой ссылке на 72 часа (план 6.1, поток 4):
```
vercel env pull .env.production.local     # переменные прода
pnpm admin:owner-link +7 701 123 45 67 --note "семья-пилот"
```
- Команда добавляет номер в `allowed_owners` (право создавать события) и печатает ссылку.
- Ссылку отправить **со своего WhatsApp** хозяину.
- Повторный вызов даёт новую ссылку; старая, если не использована, работает до срока.
- После этого удалить `.env.production.local`.

## 5. Отзыв доступа и сессий

- **Составитель потерял телефон.** Хозяин: «Тізімді кім толтырады» → карточка составителя → **«Құрылғылардан шығару»**: доступ к этому тою закрыт на всех его устройствах. Затем «Жаңа сілтеме» (старая ссылка закрывается) → «WhatsApp-қа жіберу» на новый телефон.
- **Составитель больше не участвует.** Та же карточка → **«Тойдан алып тастау»**: доступ закрыт, неиспользованные ссылки отозваны, добавленные им гости остаются в списке.
- **Все сессии одного человека** (например, украли телефон хозяина), консоль Neon → SQL Editor, ветка прода:
  ```sql
  update sessions set revoked_at = now()
  where revoked_at is null and user_id = (select id from users where phone = '+77011234567');
  ```
  Человек войдёт снова по SMS-коду или по новой ссылке (раздел 4).
- **Все сессии сразу** (подозрение на утечку базы или cookie): та же команда без условия по `user_id`. Предупредить хозяина пилота, что всем нужно войти заново.

## 6. Смена секретов

Секреты — только в Vercel (Project → Settings → Environment Variables) и в GitHub Secrets. В репозитории только пустой `.env.example`.

| Секрет | Что будет при смене | Порядок |
|---|---|---|
| `SESSION_SECRET` | Ломаются только неиспользованные подписанные ссылки загрузки музыки (живут минуты). Сессии хранятся как `sha256(token)` и **не** выходят | новое значение (`openssl rand -base64 32`) → Vercel Production → Redeploy |
| `OTP_HMAC_SECRET` | Коды, отправленные в последние минуты, перестают подходить; счётчики лимитов начинаются заново | то же |
| `CRON_SECRET` | Vercel Cron сам шлёт новое значение после Redeploy | то же; проверить ручной вызов `GET /api/cron/cleanup` с заголовком `Authorization: Bearer …` → 200 |
| `DATABASE_URL*` (пароль Neon) | Neon → Roles → Reset password → обновить оба URL в Vercel и `PROD_DATABASE_URL_UNPOOLED` в GitHub | Redeploy; проверить `/api/health` |
| `S3_*` (R2) | Новый токен R2 только на медиабакет → Vercel → Redeploy → отозвать старый токен | проверить загрузку музыки в настройках тестового тоя |
| `SMSC_*` / `MOBIZON_*` | — | Redeploy; `pnpm sms:test` на номер из `SMS_TEST_ALLOWLIST` |
| `BACKUP_*`, ключ `age` | Новая пара `age-keygen`: открытый ключ → `BACKUP_AGE_RECIPIENT`. **Старый закрытый ключ хранить**, пока живут бэкапы, сделанные им (30 дней) | Actions → «Backup production database» → Run workflow; проверить файл в R2 |
| `SENTRY_DSN` | — | Redeploy |

После любой смены: `/api/health` → `ok`, вход по SMS на свой номер, открытие своего тоя.

## 7. Сайт упал в день отправки приглашений

Цель — чтобы гости могли открыть приглашение и ответить. Всё остальное может подождать.

1. **Проверить, что именно не работает** (2 минуты):
   - `…/api/health`: `ok` — приложение живо; ошибка или таймаут — Vercel или база;
   - ссылка гостя `/i/…` с телефона;
   - Vercel → Deployments (последний деплой красный?) → Logs;
   - Neon → Monitoring (база спит, лимит CU, недоступна?);
   - Sentry (новые ошибки за последние минуты);
   - статус-страницы: vercel-status.com, neonstatus.com, cloudflarestatus.com.
2. **Сломалось после выпуска** → раздел 2: Promote предыдущего деплоя. Это самый быстрый способ.
3. **База недоступна или исчерпан лимит Neon** → Neon → поднять лимит compute / сменить тариф (по решению основателя). Ответы гостей при недоступной базе не сохраняются: страница покажет ошибку, гость сможет повторить позже.
4. **Не приходят SMS-коды** — вход составителей. Это не мешает гостям.
   - Составители входят **по ссылке** из WhatsApp: хозяин в «Тізімді кім толтырады» → карточка → «Жаңа сілтеме» → «WhatsApp-қа жіберу».
   - Проверить баланс SMSC.kz; при сбое — `SMS_PROVIDER=mobizon` в Vercel → Redeploy.
5. **Отправка из WhatsApp:** приглашения отправляются с телефонов семьи, у сервиса нет своей рассылки. Если сайт лежит — **попросить семью подождать с отправкой**, а не отправлять ссылки, которые не открываются.
6. **Музыка не играет или не загружается** (R2) — приглашение работает и без музыки. Не трогать в день отправки.
7. После восстановления:
   - написать хозяину пилота, что всё работает;
   - проверить ответы, пришедшие за время сбоя («Қорытынды», «Шақырулар»);
   - коротко записать в `docs/phases/RA-handover.md` (или в журнал инцидентов): время, причина, что сделали.

## 8. Регулярное

- **Ежедневно автоматически:**
  - Vercel Cron `/api/cron/cleanup` (03:00 Алматы): старые коды, лимиты, ссылки, сессии, брошенная музыка;
  - бэкап (02:30).
- **Раз в неделю на пилоте:**
  - Actions → последние запуски «Backup production database» зелёные;
  - Sentry без новых повторяющихся ошибок;
  - Neon — расход CU (опрос итогов затухает до 60 с, РА Л2).
- **Раз в месяц и перед тоем:** пробное восстановление (раздел 3) в новую ветку Neon с проверкой; результат записать.
